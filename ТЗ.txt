# Техническое задание: личная карта путешествий

## 1. Описание проекта

Разработать личный веб-сервис для двух человек — меня и моей девушки. Сервис представляет собой интерактивную карту, на которой можно отмечать места, где мы были, указывать даты посещения, добавлять описания и фотографии.

Основная задача — создать красивую, минималистичную и удобную карту наших путешествий и совместных воспоминаний.

Сервис предназначен для личного использования. Ожидаемая нагрузка — 1–3 пользователя в день.

**Главные приоритеты:**
- Минималистичный и приятный интерфейс.
- Удобное использование на смартфоне.
- Быстрое добавление и просмотр мест.
- Простота разработки и сопровождения.
- Надёжное хранение данных и фотографий.
- Возможность постепенно добавлять функциональность без переписывания проекта.

Не нужно создавать универсальную социальную сеть, публичную платформу или сложную систему управления путешествиями.

---

## 2. Технологический стек

Использовать следующий стек.

### Backend
- Python.
- Django.
- Django Templates для рендеринга HTML.
- Django ORM для работы с базой данных.
- Gunicorn для запуска приложения в production.

### Frontend
- HTML.
- CSS.
- Vanilla JavaScript.
- Leaflet для интерактивной карты.

### База данных
- PostgreSQL.
- Не использовать PostGIS на первом этапе.
- Координаты хранить в обычных числовых полях.

### Хранение фотографий
- Локальная файловая система.
- Pillow для обработки изображений и создания миниатюр.
- Постоянный Docker volume для хранения загруженных файлов.

### Инфраструктура
- Docker.
- Docker Compose.
- Отдельный контейнер Django-приложения.
- Отдельный контейнер PostgreSQL.
- В будущем — отдельный контейнер Telegram-бота.

### Запрещённые технологии без моего согласования
- React.
- Vue.
- Angular.
- Django REST Framework.
- Redis.
- Celery.
- RabbitMQ.
- Kubernetes.
- Nginx.
- Микросервисная архитектура.
- PostGIS.

Не добавлять новые технологии и зависимости без реальной необходимости.

Для небольшого личного проекта приоритетом является простота, а не архитектурная сложность.

---

## 3. Общая архитектура

Приложение должно быть монолитным Django-проектом.

На первом этапе достаточно двух основных контейнеров:

1. `web` — Django и Gunicorn.
2. `db` — PostgreSQL.

В дальнейшем допускается добавление контейнера `bot` для Telegram-бота.

Все контейнеры должны запускаться через Docker Compose.

Приложение должно использовать Django Templates, а не отдельное SPA-приложение.

JavaScript используется для взаимодействия с картой, модальными окнами, предварительного просмотра фотографий и других небольших клиентских функций.

Не создавать отдельный REST API без необходимости.

### Принцип расширяемости

Несмотря на простую архитектуру, необходимо заранее предусмотреть возможность добавления подтверждения изменений через Telegram.

Для этого:
- Бизнес-логику создания, изменения и удаления мест необходимо вынести в сервисный слой.
- Операции с фотографиями также должны выполняться через отдельные функции или сервисы.
- Представления Django не должны содержать всю бизнес-логику непосредственно.
- Логику сохранения данных необходимо организовать так, чтобы впоследствии можно было добавить промежуточный этап подтверждения изменений.

**Важно:** на первом этапе все изменения сохраняются сразу. Telegram-бот, очередь заявок и подтверждение изменений пока не реализуются.

# 4. Функциональные требования

## 4.1. Главная страница

После успешной авторизации пользователь попадает на страницу с интерактивной картой.

Основные элементы:
- Карта.
- Маркеры сохранённых мест.
- Кнопка добавления нового места.
- Поиск мест.
- Панель или карточка с информацией о выбранном месте.
- Возможность просмотра фотографий.
- Удобная навигация на мобильных устройствах.

Карта должна занимать основную часть экрана.

Интерфейс должен быть минималистичным, без большого количества кнопок, меню и ненужных элементов.

### Поведение карты

- При открытии карты отображаются все сохранённые места.
- Каждое место представлено маркером.
- При нажатии на маркер открывается карточка места.
- Если у места несколько фотографий, пользователь может просматривать их.
- Если у места нет фотографий, карточка должна отображаться корректно.
- Карта должна поддерживать масштабирование и перемещение.
- Если сохранено несколько мест, должна быть возможность быстро перейти к нужному маркеру.
- При необходимости можно добавить автоматическое позиционирование карты так, чтобы были видны все сохранённые места.

Использовать Leaflet.

Для картографической подложки выбрать OpenStreetMap или совместимого провайдера, учитывая его условия использования, требования к атрибуции и ограничения на количество запросов.

Не загружать тайлы карты без необходимости и не использовать публичные серверы вопреки их правилам.

---

## 4.2. Модель места

Создать модель `Place`.

Предполагаемые поля:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `id` | BigAutoField | Да | Первичный ключ |
| `title` | CharField, max_length=200 | Да | Название места |
| `description` | TextField | Нет | Описание |
| `latitude` | FloatField | Да | Широта |
| `longitude` | FloatField | Да | Долгота |
| `start_date` | DateField | Нет | Дата начала посещения |
| `end_date` | DateField | Нет | Дата окончания посещения |
| `created_at` | DateTimeField | Да | Дата создания записи |
| `updated_at` | DateTimeField | Да | Дата последнего изменения |

Для `created_at` использовать автоматическое заполнение при создании записи.

Для `updated_at` использовать автоматическое обновление при изменении записи.

### Ограничения

- Широта должна находиться в диапазоне от -90 до 90.
- Долгота должна находиться в диапазоне от -180 до 180.
- Дата окончания не может быть раньше даты начала, если обе даты указаны.
- Название места обязательно.
- Описание может быть пустым.
- Даты могут быть пустыми.

Валидацию необходимо выполнять на сервере, а не только на клиенте.

Не использовать географические расширения PostgreSQL на первом этапе.

---

## 4.3. Создание места

Пользователь должен иметь возможность добавить новое место непосредственно с карты.

### Основной сценарий

1. Пользователь нажимает кнопку добавления места.
2. Интерфейс переходит в режим выбора координат.
3. Пользователь нажимает на нужную точку карты.
4. На карте появляется предварительный маркер.
5. Открывается форма создания места.
6. Пользователь указывает название.
7. При необходимости заполняет описание и даты.
8. При необходимости прикрепляет фотографии.
9. Нажимает кнопку сохранения.
10. Сервер проверяет данные и сохраняет место.
11. Новое место появляется на карте без необходимости вручную перезагружать страницу, если это возможно в рамках простой реализации.

Пользователь должен иметь возможность изменить выбранные координаты до сохранения.

Если пользователь отменил создание, предварительный маркер необходимо убрать.

### Форма создания

Поля:
- Название.
- Описание.
- Дата начала посещения.
- Дата окончания посещения.
- Фотографии.
- Координаты.

Координаты можно отображать в форме необязательно, но пользователь должен иметь возможность выбрать точку на карте и скорректировать её.

### Поиск места

Предусмотреть возможность поиска места по названию или адресу, чтобы не всегда приходилось искать нужную точку вручную.

Для поиска можно использовать внешний геокодер.

Геокодирование не является встроенной функцией Leaflet, поэтому его необходимо реализовать отдельно.

При выборе результата поиска:
- Карта перемещается к найденной точке.
- Масштаб карты увеличивается до подходящего значения.
- Пользователь может скорректировать точку перед сохранением.

Выбрать провайдера геокодирования с учётом его условий использования, ограничений и требований к атрибуции.

Если реализация поиска существенно усложняет первый этап, допускается сначала сделать выбор точки нажатием на карту, а поиск добавить отдельным этапом.

---

## 4.4. Просмотр места

При нажатии на маркер пользователь должен видеть карточку с информацией о месте.

Карточка содержит:
- Название.
- Описание.
- Даты посещения.
- Фотографии.
- Кнопку редактирования.
- Кнопку удаления.

Если даты не указаны, не нужно отображать пустые поля или заглушки без необходимости.

Если описание отсутствует, карточка должна выглядеть аккуратно.

Если фотографий несколько, предусмотреть удобный просмотр галереи.

При нажатии на фотографию можно открывать её в увеличенном размере.

На мобильных устройствах карточка должна быть удобной для просмотра одной рукой.

---

## 4.5. Редактирование места

Пользователь должен иметь возможность изменить существующее место.

Доступные изменения:
- Название.
- Описание.
- Даты посещения.
- Координаты.
- Фотографии.

После сохранения:
- Изменения сохраняются в PostgreSQL.
- Маркер обновляется на карте.
- Карточка отображает актуальные данные.
- При изменении координат маркер перемещается на новую позицию.

Редактирование не должно создавать дубликат места.

Если пользователь отменяет редактирование, несохранённые изменения не должны применяться.

---

## 4.6. Удаление места

Пользователь должен иметь возможность удалить место.

Перед удалением необходимо показать подтверждение действия.

После подтверждения:
- Место удаляется из базы данных.
- Маркер исчезает с карты.
- Карточка закрывается.
- Связанные фотографии удаляются с файловой системы.
- Записи фотографий удаляются из базы данных.

Удаление должно быть реализовано аккуратно: нельзя оставлять бесконтрольные файлы на диске.

Учитывать, что файловая система и база данных не поддерживают общую транзакцию. Предусмотреть обработку ошибок при удалении файлов.

# 5. Фотографии

## 5.1. Общие требования

У одного места может быть несколько фотографий.

Фотографии должны храниться локально на сервере, а не в S3 или другом объектном хранилище.

Файлы должны сохраняться в постоянном Docker volume, чтобы не исчезать при пересоздании контейнера.

Не хранить изображения непосредственно в PostgreSQL.

## 5.2. Модель Photo

Создать модель `Photo`.

Предполагаемые поля:

| Поле | Тип | Описание |
|---|---|---|
| `id` | BigAutoField | Первичный ключ |
| `place` | ForeignKey | Связанное место |
| `image` | ImageField | Оригинальное изображение |
| `thumbnail` | ImageField | Миниатюра |
| `original_filename` | CharField | Исходное имя файла |
| `caption` | CharField | Подпись к фотографии, необязательно |
| `mime_type` | CharField | Определённый тип изображения |
| `size_bytes` | PositiveBigIntegerField | Размер файла |
| `sort_order` | PositiveIntegerField | Порядок отображения |
| `created_at` | DateTimeField | Дата загрузки |

При удалении места связанные записи фотографий должны удаляться, но одной настройки удаления записей в ORM недостаточно для очистки физических файлов.

Удаление файлов необходимо обрабатывать отдельно.

## 5.3. Загрузка фотографий

Пользователь должен иметь возможность:
- Загружать одну фотографию.
- Загружать несколько фотографий за один раз.
- Видеть предварительный просмотр выбранных фотографий.
- Отменять выбор до отправки формы.
- Удалять фотографии у существующего места.
- Добавлять новые фотографии к существующему месту.

Предварительный просмотр реализовать на Vanilla JavaScript с использованием `URL.createObjectURL`.

Созданные временные URL освобождать через `URL.revokeObjectURL`, когда они больше не нужны.

## 5.4. Обработка изображений

При загрузке:
- Проверять фактическое содержимое файла, а не доверять только расширению или MIME-типу, указанному браузером.
- Разрешать только поддерживаемые форматы изображений.
- Ограничивать размер файла.
- Ограничивать количество файлов за одну загрузку.
- При необходимости ограничивать суммарный размер загружаемых файлов.
- Генерировать безопасные имена файлов.
- Не использовать переданные пользователем имена файлов как пути хранения.
- Создавать миниатюры через Pillow.
- Учитывать EXIF-ориентацию изображений.
- Обрабатывать ошибки декодирования и сохранения файлов.

Конкретные лимиты размера и количества фотографий вынести в настройки или конфигурацию приложения, если это не усложняет реализацию.

Для начала можно использовать разумные значения, например:
- До 10 фотографий за одну загрузку.
- До 15 МБ на один файл.

Значения должны быть легко изменяемыми.

Оригиналы необходимо сохранять в хорошем качестве. Миниатюры использовать в списках и карточках, чтобы не загружать большие файлы без необходимости.

## 5.5. Структура файлов

Предлагаемая структура:

```text
media/
└── places/
    └── <place_id>/
        ├── originals/
        │   ├── <generated_filename>.jpg
        │   └── ...
        └── thumbnails/
            ├── <generated_filename>.webp
            └── ...
```

Допускается другая структура, если она безопаснее или удобнее.

Пользователь не должен управлять путями хранения файлов вручную.

## 5.6. Доступ к фотографиям

Поскольку сервис закрытый, фотографии не должны быть доступны посторонним только по прямому URL.

Необходимо обеспечить защиту оригиналов и миниатюр.

В production нельзя бездумно публиковать весь каталог `media` через общедоступный статический сервер.

Использовать контролируемую выдачу файлов через Django или другое простое решение, совместимое с выбранной архитектурой.

Учитывать, что проверка авторизации только на странице с карточкой недостаточна: доступ к файлам тоже должен быть защищён.

# 6. Авторизация

## 6.1. Общая концепция

На первом этапе нужна одна общая парольная защита всего сайта.

Отдельные аккаунты, регистрация, восстановление пароля и разграничение ролей не нужны.

Пароль задаётся через переменную окружения в `.env`.

Пример названия переменной:

```env
SITE_PASSWORD=change-me
```

Пример приведён только для демонстрации. В реальном окружении необходимо использовать собственный сильный пароль.

Пароль не должен:
- Храниться в Git.
- Попадать в исходный код.
- Встраиваться в HTML или JavaScript.
- Выводиться в логах.
- Передаваться клиенту после успешной авторизации.

## 6.2. Поведение авторизации

- При открытии закрытой страницы неавторизованный пользователь перенаправляется на страницу входа.
- Пользователь вводит общий пароль.
- После успешной проверки создаётся Django-сессия.
- После авторизации пользователь получает доступ к карте и всем функциям.
- При выходе сессия завершается.
- Неверный пароль не должен предоставлять доступ к данным.

Необходимо защищать не только главную страницу, но и все маршруты, включая:
- Создание мест.
- Редактирование.
- Удаление.
- Загрузку фотографий.
- Просмотр фотографий.
- Выдачу оригиналов и миниатюр.
- Любые служебные страницы приложения.

## 6.3. Безопасность авторизации

Обязательно:
- Использовать Django sessions.
- Использовать CSRF-защиту для изменяющих запросов.
- Ограничивать частоту попыток входа простым механизмом, подходящим для небольшого проекта.
- Использовать безопасные настройки cookie в production.
- Использовать HTTPS в production.
- Не сообщать лишнюю информацию при ошибке авторизации.
- Завершать сессию при выходе.

Секретный ключ Django также должен передаваться через переменную окружения.

В production должны быть выключены `DEBUG` и другие небезопасные настройки разработки.

### Важный нюанс

Необходимо согласовать поведение сессии с требованием личного доступа.

Желательно, чтобы при новом открытии сайта после закрытия браузера пользователь снова вводил пароль.

Однако обычная Django-сессия может сохраняться в некоторых сценариях, в зависимости от конфигурации браузера и cookie.

Нужно проверить фактическое поведение и выбрать подходящую конфигурацию. Не заявлять, что повторный вход гарантирован, пока это не протестировано.

# 7. Пользовательский интерфейс

## 7.1. Общий стиль

Интерфейс должен быть:
- Минималистичным.
- Современным.
- Аккуратным.
- Визуально лёгким.
- Удобным для смартфонов.
- Без лишних элементов управления.

Карта — главный элемент интерфейса.

Не использовать тяжёлые UI-библиотеки без необходимости.

Можно использовать небольшие CSS-анимации и плавные переходы, если они не мешают работе.

## 7.2. Мобильная версия

Мобильная версия обязательна.

Необходимо проверить интерфейс на небольшом экране.

- Формы не выходят за границы экрана.
- Карточка места открывается в виде нижней панели или удобного мобильного блока.

# 8. Подготовка к будущему подтверждению через Telegram

Этот раздел описывает будущее развитие проекта.

**На первом этапе ничего из этого раздела реализовывать не нужно, кроме подготовки сервисного слоя.**

В будущем предполагается следующий процесс:

1. Пользователь создаёт, редактирует или удаляет место.
2. Изменение не применяется сразу.
3. Создаётся заявка на изменение.
4. Telegram-бот отправляет уведомление администратору.
5. Администратор одобряет или отклоняет заявку.
6. При одобрении изменение применяется.
7. При отклонении текущие данные остаются без изменений.

Подтверждение должно распространяться на все операции:
- Создание места.
- Изменение места.
- Удаление места.
- Добавление фотографий.
- Удаление фотографий.
- Изменение набора фотографий.

Важное требование: будущая архитектура должна позволять внедрить этот процесс без полной переработки существующих представлений, моделей и операций с файлами.

## 8.1. Предполагаемая модель ChangeRequest

В будущем можно добавить модель `ChangeRequest` со следующими полями:

| Поле | Описание |
|---|---|
| `id` | Идентификатор заявки |
| `action` | Тип действия: CREATE, UPDATE или DELETE |
| `entity_type` | Тип сущности |
| `entity_id` | Идентификатор изменяемой сущности, если существует |
| `payload` | JSON с необходимыми данными изменения |
| `status` | Статус заявки |
| `created_at` | Дата создания |
| `resolved_at` | Дата принятия решения |
| `telegram_message_id` | Идентификатор сообщения Telegram, если применимо |
| `error_message` | Информация об ошибке, если применимо |

Возможные статусы:
- `PENDING` — ожидает решения.
- `APPROVED` — одобрена.
- `REJECTED` — отклонена.
- `APPLIED` — изменение применено.
- `FAILED` — возникла ошибка при применении.
- `EXPIRED` — срок действия заявки истёк.

Окончательный состав полей и статусов можно определить на этапе реализации Telegram-функциональности.

## 8.2. Фотографии в заявках

При будущей реализации подтверждения необходимо учитывать, что фотографии нельзя бездумно сохранять как окончательные до одобрения заявки.

Предлагаемый подход:
- Временно сохранять загруженные файлы в отдельном каталоге заявок.
- При одобрении переносить файлы в постоянное хранилище.
- При отклонении удалять временные файлы.
- Предусмотреть очистку файлов при ошибках и отменённых заявках.

На первом этапе временное хранилище заявок не требуется.

## 8.3. Будущий Telegram-бот

В будущем бот будет работать в отдельном контейнере Docker Compose и использовать тот же Django-проект, базу данных и бизнес-логику.

Токен бота и Telegram ID администратора должны храниться в переменных окружения.

При обработке действий бот должен проверять:
- Telegram ID пользователя, который нажал кнопку.
- Существование заявки.
- Текущий статус заявки.
- Допустимость операции в текущем состоянии.

Нельзя полагаться только на наличие кнопки в сообщении Telegram как на механизм авторизации.

Обработка повторных нажатий должна быть безопасной: одна заявка не должна применяться несколько раз.

Ошибки Telegram API и временные сбои не должны приводить к потере заявок.

Механизм доставки уведомлений и повторных попыток следует выбрать на этапе реализации бота. Для небольшой нагрузки можно рассмотреть простое хранение состояния и опрос PostgreSQL без добавления Redis или брокера сообщений.

Бот не должен обходить сервисный слой и напрямую менять данные в обход общей бизнес-логики.

На первом этапе сервисы должны выполнять изменения сразу.

# 11. Docker и запуск

Проект должен запускаться через Docker Compose.

Минимально необходимые сервисы:

### `web`
- Python.
- Django.
- Gunicorn.
- Код приложения.
- Доступ к PostgreSQL.
- Доступ к постоянному хранилищу фотографий.

### `db`
- PostgreSQL.
- Постоянный Docker volume для данных базы.

В `compose.yaml` должны быть описаны сервисы, зависимости, переменные окружения и необходимые тома.

Не хранить пароль базы данных и другие секреты непосредственно в Git.

Подготовить `.env.example` с названиями необходимых переменных и безопасными примерами значений.

Реальный `.env` должен находиться в `.gitignore`.

Подготовить понятную инструкцию запуска в `README.md`.

Минимальный сценарий:
1. Создать `.env`.
2. Собрать контейнеры.
3. Запустить PostgreSQL и Django.
4. Применить миграции.
5. Создать необходимые начальные данные, если они требуются.
6. Открыть сайт в браузере.

В production необходимо запускать приложение через Gunicorn, а не через Django development server.

Не добавлять Nginx.

HTTPS должен обеспечиваться выбранным хостингом, платформой или отдельным внешним механизмом. Нельзя считать приложение безопасным для публичного production только потому, что оно запускается через Docker.

# 13. Безопасность

Безопасность важна даже для личного проекта.

Обязательные требования:
- Защищать все страницы и конечные точки, включая доступ к фотографиям.
- Использовать CSRF-защиту Django.
- Изменять данные только через POST-запросы или другие подходящие методы изменения состояния, но не через GET.
- Проверять входные данные на сервере.
- Проверять координаты и даты.
- Проверять содержимое и размер изображений.
- Не использовать пользовательские имена файлов как пути.
- Не раскрывать секреты в HTML, JavaScript и логах.
- Не коммитить `.env`.
- Ограничивать перебор пароля.
- Обрабатывать ошибки базы данных и файловой системы.
- Не показывать пользователю stack trace в production.
- Не выдавать файлы из `media` публично без проверки авторизации.
- Использовать HTTPS при внешнем доступе.

Для удаления и сохранения файлов учитывать частичные ошибки. Не предполагать, что операции с PostgreSQL и файловой системой атомарны.

По возможности предусмотреть понятное логирование ошибок без секретов и содержимого паролей.

# 14. Производительность и простота

Ожидаемая нагрузка небольшая.

Поэтому:
- Не оптимизировать преждевременно.
- Не добавлять Redis.
- Не добавлять отдельные очереди задач.
- Не использовать микросервисы.
- Не создавать сложную систему кэширования.
- Не использовать отдельный frontend framework.
- Не создавать API без необходимости.

При этом:
- Не загружать оригиналы фотографий для всех маркеров.
- Использовать миниатюры там, где это уместно.
- Не выполнять ненужные запросы к базе данных.
- Избегать очевидных проблем N+1.
- Не загружать весь архив фотографий до того, как пользователь открыл соответствующее место.

Решения должны оставаться простыми, но не быть заведомо ненадёжными.

# 16. Этапы разработки

После каждого этапа необходимо остановиться, предоставить отчёт и дождаться моего подтверждения перед переходом к следующему этапу.

- Настройку PostgreSQL для локального запуска.

- Виртуальное окружение создаётся и активируется.
- Зависимости устанавливаются.

- Обработку повторных нажатий и ошибок.
- Повторные попытки отправки уведомлений при необходимости.

На этом этапе приложение всё ещё должно корректно запускаться локально без Docker.

### Критерии готовности

- Отклонённые заявки не изменяют текущие данные.
- Одобренные заявки применяются корректно.
- Нельзя одобрить заявку от имени постороннего пользователя.
- Повторная обработка заявки не приводит к дублированию изменений.
- Ошибки не приводят к бесконтрольной потере файлов.

- Постоянный Docker volume для фотографий.
- Запуск Django через Gunicorn.
- Применение миграций при развёртывании по понятному и безопасному сценарию.
- Инструкцию запуска через Docker Compose.
- Production-настройки Django.
- Настройку `ALLOWED_HOSTS`.
- Настройки HTTPS и защищённых cookie для production.
- Инструкцию по резервному копированию и восстановлению базы данных и фотографий.

При переносе в Docker необходимо сохранить возможность обычного локального запуска без Docker, если для этого нет объективных технических причин.

Не добавлять Nginx.

### Критерии готовности
- Приложение запускается локально без Docker.
- Приложение также запускается через Docker Compose.
- Django подключается к PostgreSQL в обоих сценариях.
- Фотографии сохраняются в постоянном хранилище и не пропадают при пересоздании контейнеров.
- `DEBUG=False` в production.
- Секреты не хранятся в Git.
- Резервную копию можно восстановить по инструкции.
- Основная функциональность работает после переноса в Docker.

# 18. Правила работы AI-разработчика

AI-разработчик должен соблюдать следующие правила.

## 18.1. Строгая поэтапность

Работать только над текущим этапом.

Перед началом этапа:
1. Кратко описать план.
2. Перечислить предполагаемые изменения.
3. Указать зависимости и потенциальные риски.

После завершения:
1. Перечислить созданные и изменённые файлы.
2. Описать реализованную функциональность.
3. Перечислить выполненные команды.
4. Сообщить результаты тестирования.
5. Указать известные ограничения и нерешённые проблемы.
6. Дождаться моего подтверждения.

Не переходить к следующему этапу самостоятельно.

## 18.2. Сохранение существующего кода

- Не переписывать работающий код без необходимости.
- Не удалять существующую функциональность ради упрощения.
- Не менять архитектуру без согласования.
- Не заменять выбранные технологии другими без моего разрешения.
- Не добавлять новые зависимости без объяснения необходимости.
- Перед существенными изменениями объяснять, зачем они нужны.

## 18.3. Качество реализации

- Использовать Django ORM.
- Использовать миграции.
- Проверять данные на сервере.
- Использовать CSRF-защиту.
- Не хранить секреты в исходном коде.
- Обрабатывать ошибки файловой системы.
- Учитывать ограничения транзакций между базой данных и файлами.
- Не дублировать бизнес-логику в разных представлениях.
- Не создавать чрезмерно абстрактную архитектуру.
- Писать понятный код, который можно сопровождать без сложной документации.

## 18.4. Контроль объёма

Не реализовывать функции из будущих этапов заранее.

В частности:
- На первых этапах не реализовывать Telegram-бота.
- Не создавать очередь подтверждений.
- Не внедрять Redis или Celery.
- Не добавлять REST API без необходимости.
- Не добавлять отдельный frontend framework.
- Не создавать дополнительные сервисы без необходимости.

Единственное исключение — простая подготовка сервисного слоя, необходимая для будущего подтверждения изменений.

## 18.5. Достоверность отчётов

Не заявлять, что функциональность работает, только потому, что код написан.

Если невозможно выполнить команду или проверить функциональность, прямо указать это.

Не скрывать ошибки тестов.

Если обнаружена проблема за пределами текущего этапа, описать её и согласовать дальнейшие действия.
